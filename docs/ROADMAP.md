## Главный принцип: любая связка провайдеров

Логика не должна быть завязана на пару Cardaq ↔ Corefy. Связка может быть любой: **Cardaq ↔ Corefy**, **Madfin ↔ Corefy**, эквайер без шлюза, и так далее. Новый провайдер добавляется так:

1. **Парсер формата отчёта.** Один класс.
2. **Коннектор бота.** Один класс плюс скрипт Playwright.
3. **Запись в админке.** Провайдер: тип, себестоимость, часовой пояс, правила сверки.

Ядро (приём, сверка, расчёт, отчёты) ничего не знает о конкретных провайдерах и работает по их **роли**.

### Роли провайдеров

| Роль | Что даёт | Примеры | Себестоимость применяется к |
| --- | --- | --- | --- |
| `bank` (эквайер / клиринг) | Клиринговые операции: суммы, ARN, регион, продажи, возвраты, чарджбэки | Cardaq, Madfin | операциям этого эквайера |
| `gate` (шлюз / процессинг) | Операции шлюза: ID платежа, email, отказы, статусы | Corefy | операциям этого шлюза |
| `crypto` | Конвертация выплаты в USDC | Oxen | чистому объёму выплаты |

У каждого MID уже есть `bank_provider_id` и `gate_provider_id`. **Эта пара и определяет связку:** какие файлы ждать, кого с кем сверять, чью себестоимость брать. Если у MID нет шлюза, отчёт считается только по эквайеру.

### Что поменять в схеме (первым делом на этапе 3)

База ещё не в продакшене, поэтому правим исходные миграции, а не добавляем новые поверх.

| Где | Было | Станет |
| --- | --- | --- |
| `merchant_operations.source` | enum `cardaq` / `corefy` | `provider_id` (FK на `providers`) + `role` (`bank` / `gate`) |
| `merchant_operations` | `ex_id` | **`sp_id`** (уже переименовано) — ID операции у провайдера другой стороны связки, найденный сверкой; `sp_id` у одной стороны указывает на другую, и наоборот |
| `merchant_operations` | — | `matched_operation_id` (FK на найденную пару), `card_bin`, `card_last4`, `raw` (JSON исходной строки) |
| `daily_report_tasks` | `is_cardaq_received`, `is_corefy_received`, `cardaq_file_path`, `corefy_file_path` | убрать; вместо них таблица **`daily_report_sources`** |
| **`daily_report_sources`** (новая) | — | `daily_report_task_id`, `provider_id`, `role`, `file_path`, `received_at`, `rows_count`, `bot_run_id`; уникальный ключ `(task, provider)` |
| `providers` | — | `report_format` (ключ парсера: `cardaq`, `corefy`, `madfin`), `connector` (ключ бота), `timezone` (например `Europe/Moscow` для UTC+3), `report_delay_days` (Cardaq — 2, Corefy — 1), `matching` (JSON с правилами сверки, см. ниже) |
| `enum OperationSource` | cardaq / corefy | удалить, вместо него `ProviderType` для роли |

## Этап 3. Ядро расчётов

Цель: из файлов провайдеров получать дневной отчёт с прибылью по каждому MID.

### 3.1 Парсеры отчётов

- Интерфейс `App\Reports\Parsers\ReportParser`:
  - `supports(string $format): bool`;
  - `reportDate(UploadedFile): ?Date` — реальная дата из файла (у Cardaq — строка «Processing date(s)»);
  - `rows(UploadedFile): iterable<OperationRow>`.
- `OperationRow` — один нормализованный DTO для всех провайдеров: `mid`, `merchant_name`, `payment_id`, `arn`, `rrn`, `card_bin`, `card_last4`, `ips`, `region`, `issuer_country`, `amount`, `currency`, `trn_type`, `resolution`, `processing_code`, `email`, `transacted_at` (уже переведено в UTC по часовому поясу провайдера), комиссии, `raw`.
- Реализации: `CardaqParser`, `CorefyParser`, потом `MadfinParser`. Каждая — только чтение колонок своего формата, без бизнес-логики.
- Реестр `ParserRegistry` выбирает парсер по `providers.report_format`.
- Поддержка CSV и XLSX (PhpSpreadsheet), потоковое чтение больших файлов.

### 3.2 Приём файлов

`ReportIngestionService::ingest(Provider $provider, UploadedFile $file, ?Date $hintDate, ?BotRun $run)`:

1. **Разбор.** Выбрать парсер, определить реальную дату отчёта, сохранить файл в `storage/app/private/reports/raw/{provider}/{дата}/`.
2. **Разбивка по MID.** Строки группируются по `mid`, для эквайера ещё и по `provider_login`.
   - MID ищется среди MID, у которых этот провайдер стоит эквайером или шлюзом.
   - **Неизвестный MID** — мерчант и MID создаются в статусе `review`, отчёт не считается, на дашборде появляется предупреждение (проблема №4 из ТЗ).
3. **Запись операций.** Каждая строка → `MerchantOperation::classify()` → upsert в `merchant_operations`. Ключ дедупликации: `provider_id + payment_id + trn_type + amount`, поэтому повторная загрузка не создаёт дублей.
4. **Задачи отчётов.** Для каждого затронутого MID создаётся или обновляется `daily_report_task` на дату из `ReportDateResolver`, файл отмечается в `daily_report_sources`.
5. **Запуск расчёта.** Когда пришли **все источники, которые нужны этому MID** (эквайер и шлюз, если он задан), в очередь ставится `GenerateDailyReportJob`. Если пришла только часть — статус `partial`.

### 3.3 Дата отчёта

`ReportDateResolver` — один сервис вместо хардкода в трёх местах (проблема №8 из ТЗ):

- Пт, Сб, Вс → отчёт на воскресенье.
- Праздники из `bank_holidays` склеиваются с соседними выходными в один отчёт.
- Для каждой даты возвращается `report_date`, `period_from`, `period_to`.
- Отдельный метод `readyOn(Provider)` учитывает `report_delay_days` провайдера: когда отчёт уже можно забирать.

### 3.4 Сверка (любая пара провайдеров)

`ReconciliationService::reconcile(MerchantMid $mid, Date $from, Date $to)` сверяет операции эквайера MID с операциями его шлюза. Правила берутся из `providers.matching`, а не из кода:

```json
{
  "keys": [["card_bin", "card_last4", "amount", "currency"], ["card_bin", "amount", "currency"]],
  "window_minutes": 5,
  "try_timezone_shift": true,
  "tie_breakers": ["email", "closest_time"]
}
```

- Ключи проверяются по очереди: сначала строгий, потом запасной.
- Время сравнивается в UTC, потому что часовой пояс уже учтён парсером. `try_timezone_shift` нужен для провайдеров, у которых зона в файлах плавает.
- Пары строго один к одному: уже сопоставленная операция больше не участвует.
- **Результат:** обеим операциям пары заполняется `matched_operation_id`, а в `sp_id` пишется ID операции другой стороны.
- Сверка запускается внутри генерации отчёта и командой `reports:reconcile` каждые 15 минут по MID, где остались несопоставленные операции.
- В карточке операции видна её пара; на экране Operations есть фильтр «без пары».

### 3.5 Генератор дневного отчёта

`DailyReportGenerator::generate(DailyReportTask $task)` — единственное место, где считается прибыль. Считаем в валюте MID через `brick/money`, без float.

1. **Операции.** Берутся из `merchant_operations` по MID и периоду отчёта.
2. **Комиссия мерчанта.** По каждой продаже: сумма × ставка (Visa/MC × EU/non-EU, иначе запасная ставка). Плюс фиксы × количество: успех, возврат, чарджбэк; отказы берутся из операций шлюза.
3. **Себестоимость.**
   - тариф эквайера MID — к операциям эквайера;
   - тариф шлюза MID — к операциям шлюза;
   - тариф крипто-провайдера мерчанта — к конвертации.
4. **Резерв.** База = продажи − возвраты − чарджбэки − комиссия; резерв = база × %, но не выше остатка до лимита MID.
   - Резерв пишется записью `hold` в `reserve_ledger_entries` с `release_on = дата + rolling_reserve_days`.
   - При перегенерации старая запись сторнируется, поэтому двойного удержания нет.
5. **Выплата и прибыль.** Чистый объём, комиссия за конвертацию, выплата мерчанту, net profit.
6. **Пересчёт в базовую валюту.** Курс MID → EUR на дату отчёта из `fx_rates` фиксируется в отчёте, заполняются `turnover_base` и `net_profit_base`. Если курса нет, отчёт получает статус `blocked` с понятной причиной.
7. **Файлы.** XLSX, PDF и CSV операций в `reports/generated/{дата}/`, письмо на `invoice_email` через очередь.

Отчёт **не считается**, пока у мерчанта не заполнен тариф, у MID нет эквайера или MID в статусе `review`. В этом случае статус `blocked` с причиной (проблема №10 из ТЗ).

### 3.6 Экран Operations

- Поиск по ARN, `payment_id`, `sp_id`, MID, карте (BIN / last4). Фильтры: провайдер, роль, тип операции, регион, валюта, даты, «без пары».
- Итоги по выборке через SQL-агрегаты, а не выборкой всего в память (проблема №11 из ТЗ).
- Карточка операции: исходная строка (`raw`), пара из другой системы, начисленные комиссии.

### 3.7 API для внешнего бота (совместимость)

- `GET /api/v1/reports/pending-tasks?provider={code}` — недостающие даты **по MID** для любого провайдера.
- `POST /api/v1/reports/upload/{provider}` — один эндпоинт для всех провайдеров.
- Токен как раньше (`VerifyBotReportToken`).

### 3.8 Тесты

- Пример из ТЗ: net profit **163.09**.
- MID в USD и GBP считаются в своей валюте; `net_profit_base` пересчитан по зафиксированному курсу.
- Две разные связки на одном стенде: Cardaq↔Corefy и Madfin↔Corefy (на фикстурах).
- Выходные, праздник, перегенерация без двойного резерва, неизвестный MID → `review`.
- Сверка: строгий ключ, запасной ключ, сдвиг времени, один к одному, выбор по email.

**Нужно от вас:** 2–3 реальных (можно обезличенных) файла Cardaq, Corefy и Madfin; коды `trn_type` для чарджбэка; часовые пояса провайдеров.

## Этап 4. Боты (коннекторы)

Каждый провайдер получает свой коннектор: `cardaq-export`, `corefy-export`, `madfin-export`, позже `oxen-transfer`.

- **Интерфейс** `App\Bots\Connector`: `code()`, `pendingTargets(): iterable<Target>`, `run(Target): BotResult`.
- **Таблица `integration_accounts`:** провайдер, URL входа, логин, пароль, TOTP-секрет (всё в зашифрованном виде), список MID, которые покрывает аккаунт, активен или нет.
- **Таблица `bot_runs`:** коннектор, аккаунт, дата отчёта, статус (`queued` / `running` / `succeeded` / `failed` / `skipped`), попытки, файл, ошибка, скриншот, длительность.
- **Браузер.** Скрипты Playwright на Node в `bots/{connector}.mjs`.
  - Laravel запускает их через `Process` из задачи `RunConnectorJob`; скрипт получает параметры в JSON, логинится, скачивает файл и возвращает путь к нему.
  - Логика ретраев и журнал — на стороне Laravel.
- **Планировщик.** Каждые 30 минут:
  - для каждого активного провайдера с коннектором берутся MID, где он эквайер или шлюз;
  - `ReportDateResolver::readyOn()` даёт даты, которые уже можно забирать;
  - задача ставится, если источника ещё нет в `daily_report_sources`. Блокировка по `(коннектор, аккаунт, дата)` исключает дубли.
- **Результат** уходит в `ReportIngestionService` (этап 3).
- **Экран «Боты»:** коннекторы и аккаунты, последние запуски, «запустить сейчас», «повторить», просмотр ошибки со скриншотом, уведомление при 3 падениях подряд.
- **Сервер:** supervisor для `queue:work`, cron для `schedule:run`, Chromium уже установлен.

**Нужно от вас:** ссылки и шаги входа для каждого портала, есть ли 2FA; какой аккаунт покрывает какие MID.

## Этап 5. Report Control Center и Settlement

- **Report Control Center.**
  - Сетка «MID × день» за месяц. Статусы: `completed`, `pending`, `partial` (показано, каких источников не хватает), `blocked` (с причиной), `failed`.
  - Итоги: оборот по валютам, к выплате, выплачено, наша комиссия.
  - Действия: перегенерировать, переотправить письмо, удалить (удаление сторнирует резерв), скачать файлы.
- **Settlement** — отдельные таблицы `settlements` и `settlement_lines`, потому что одна выплата может закрывать несколько дней и валют.
  - Строка — дневной отчёт или ручная корректировка (начисление или удержание, например «Previous Overpayment»).
  - Курс каждой валюты к USDC по умолчанию берётся последний из FX rates (проблема №9 из ТЗ), его можно поправить.
  - Статусы `draft → approved → settled`: кто одобрил, кто и когда отметил выплату, хэш транзакции, подтверждение (PDF или картинка).
  - PDF «Settlement Statement» с номером `SET-2026-000123`.
  - Отмена возвращает всё назад и пишется в аудит.
- **Возврат резерва.** Задача раз в день создаёт записи `release` по удержаниям с наступившей датой `release_on` и добавляет их в ближайший settlement.

## Этап 6. Merchant Portal и доступы

- **Вкладка «Доступы» на странице компании.** Основной логин создаётся вместе с компанией, пароль показывается один раз. Можно добавить ещё логины, сбросить пароль, отключить доступ.
- **Портал `/portal`** — мерчант видит только свою компанию и её дочерние (`Company::descendantIdsWithSelf()`):
  - KPI по каждому MID и валюте, резерв и его лимит, график;
  - дневные отчёты и settlement-выписки со скачиванием, документы;
  - смена пароля, 2FA.
- **Team & access.** Сотрудники и права по модулям. Суперадмин определяется только ролью; пустой список прав — нет доступа (проблема №2 из ТЗ). Мерчант-логины в этом разделе не показываются.

## Этап 7. Прибыль и делёжка

- **Дашборд прибыли.** Считается по завершённым дневным отчётам через SQL-агрегаты, в EUR с разбивкой по валютам и провайдерам:
  - оборот, выручка, себестоимость, net profit, маржа, сравнение с прошлым периодом;
  - график по дням, таблица мерчантов;
  - операционка: отчёты `pending` / `partial` / `blocked`, выплаты, накопленные резервы.
- **Providers & Profit.** Маржа по каждой связке провайдеров (например, Cardaq↔Corefy против Madfin↔Corefy), гео и конверсия, Visa/MC, банки-эмитенты, причины отказов.
- **Делёжка.**
  - `profit_partners` — кто получает долю.
  - `profit_share_rules` — мерчант или правило по умолчанию, партнёр, база (net profit или оборот), процент, действует с/по.
  - `monthly_statements` — черновик, потом «закрыт». Закрытый месяц не пересчитывается; PDF с долями и остатком компании, предупреждение при отрицательном остатке.

## Этап 8. oxen-transfer (движение денег)

Коннектор на том же каркасе, что и в этапе 4, но с обязательными защитами:

- перевод только по settlement в статусе `approved`;
- ключ идемпотентности на каждый перевод, повторный запуск не шлёт деньги второй раз;
- адрес получателя только из активных кошельков мерчанта (белый список);
- лимиты на один перевод и на день; выше лимита — подтверждение вторым человеком;
- режим dry-run для проверки сценария без отправки;
- хэш транзакции автоматически записывается в settlement; каждое действие — в аудит.

**Нужно от вас:** пример входа в Oxen, какие операции бот делает (обмен, перевод, вывод роллинга), кто подтверждает переводы.
